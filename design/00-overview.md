# 程序分析框架总体设计

## 结论

本项目使用 Go 实现面向 C/C++、Java、Go 和 Python 的程序分析框架。整体按照以下依赖顺序建设，并划分为前端基础阶段（模块 01–05）与分析与报告阶段（模块 06–13）：

```text
源代码
  ↓
Tree-sitter Parser
  ↓
Common AST
  ↓
符号表与名称解析
  ↓
统一 IR
  ↓
Call Graph
  ↓
类型/类层次
  ↓
函数内 SSA
  ↓
局部指针分析
  ↓
按需污点分析
  ↓
路径可达性验证
  ↓
语法模式匹配
  ↓
缺失安全检查检测
  ↓
SARIF 报告
```

Parser 负责稳定、可恢复地生成 Tree-sitter 具体语法树（CST）；Common AST 为每种语言实现 CST 到跨语言抽象语法树的规范化转换，屏蔽 grammar 差异；符号表在 common AST 之上建立作用域、声明、引用与名称解析；统一 IR 在 common AST 与符号表之上构建面向分析、带符号绑定与类型关联的语义中间表示；Call Graph 在 IR 与符号解析结果之上建立调用关系；类型/类层次在符号表之上建立类型之间的继承、实现和成员关系；函数内 SSA 在 IR 之上为每个函数体建立静态单赋值形式；局部指针分析在 SSA 之上处理对象创建、字段存取之间的别名关系，为数据流分析保证链路不断；污点分析在上述模块之上按需求解从 source 经 sanitizer 到 sink 的数据流，是当前建设的重点；符号执行通过自建轻量 IR 虚拟机解释执行统一 IR，对污点分析给出的主路径做局部符号/concolic 求解，只验证该主路径是否真实可达并剪除可证明不可达的误报；语法模式匹配在 AST 与 IR 之上用带元变量约束的模式识别硬编码口令等简单漏洞模式；缺失安全检查检测在语法模式匹配之上比较代码库中语义等价的相似片段，找出多数片段都有、个别片段缺失的安全检查（如鉴权）异常；污点分析、符号执行、语法模式匹配和缺失安全检查检测均可通过配置独立开关，关闭某项不影响其余阶段的结果与确定性；报告模块将上述结果转换为标准 SARIF 格式输出，保留可回溯源码位置的完整数据流路径。禁止后置模块绕过前置模块直接依赖 Tree-sitter 节点，否则无法形成统一的多语言分析基础。

模块 01–05 属于**前端基础阶段**，负责把源码稳定地转换为 CST、common AST、符号表、统一 IR 和调用图；模块 06–13 属于**分析与报告阶段**，在前端基础之上依次建立类型层次、函数内 SSA、局部指针分析、按需污点分析、主路径可达性验证、语法模式匹配、缺失安全检查检测，并最终输出 SARIF 报告。分析与报告阶段的每个模块都必须建立在已验证的前端基础之上，不得反向依赖。

Common AST 与统一 IR 是两层不同抽象，职责必须划清：common AST 尽量无损地把各语言 CST 规范化为跨语言统一命名的语法树，与源码结构一一对应；统一 IR 在 common AST 与符号表之上做面向分析的语义规范化（desugar、显式化隐式操作、规范化控制流），可有损或增补。符号表建立在 common AST 之上，统一 IR 建立在 common AST 与符号表之上，因此符号表先于统一 IR 构建。

每个模块的实现、单元测试、E2E 测试、fixture 和专用脚本必须收拢在对应实现目录内。模块之间只通过公开接口连接，后置模块不得跨目录访问前置模块的私有结构或测试数据。

## 目标

- 支持解析 C、C++、Java、Go 和 Python 项目。
- 使用 Tree-sitter 作为统一语法解析基础，保留源码位置、语法错误和语言特有信息。
- 为每种语言建立 CST 到跨语言 common AST 的规范化转换，屏蔽 grammar 差异。
- 建立统一符号表，表达文件、包、命名空间、类型、函数、方法、变量、字段和参数等符号。
- 完成声明绑定、引用解析、类型关联和跨文件符号合并。
- 在 common AST 与符号表之上建立面向分析的统一 IR，供后续程序分析模块复用。
- 基于统一 IR 与符号表生成 Call Graph，并保留调用点和解析依据。
- 保证前端结果可测试、可序列化、可追踪回原始源码。
- 以低误报为最低要求：必须存在有效正报，测试集误报率必须低于 30%。

## 非目标

- 本项目不实现完整编译器，不要求生成机器码或可执行文件。
- 本项目不保证完全复现 Clang、`javac`、Go 编译器或 CPython 的全部语义与错误诊断行为。
- 分析与报告阶段只提供函数内 SSA、局部指针分析、按需污点分析、语法模式匹配和缺失安全检查检测；不实现全程序过程间数据流分析、完整指针分析和通用过程间控制流分析，这些更强能力在前述模块稳定后单独设计。
- 本项目不以格式化、代码重写或代码生成作为主要目标。
- 不允许为了统一而丢弃语言特有语义；无法统一的语义必须通过明确的语言扩展字段保留。

## 使用场景

- 对多语言代码库进行结构化扫描与索引。
- 查询函数、方法、类型、变量和字段的定义与引用。
- 构建跨文件、跨包和跨模块的调用关系。
- 为漏洞模式检测、代码审计、依赖分析和后续数据流分析提供统一输入。
- 从分析结果准确定位到源文件、行列范围和原始语法节点。

## 模块边界

### Parser

Parser 只负责语法层工作：

- 根据语言选择对应的 Tree-sitter grammar。
- 解析源文件并输出 Tree-sitter concrete syntax tree。
- 统一记录文件标识、字节区间、行列位置、缺失节点和错误节点。
- 提供遍历、节点查询和源码切片能力。
- 不负责跨文件名称解析、类型求值或调用目标推断。

### Common AST

Common AST 负责把各语言 CST 规范化为跨语言抽象语法树：

- 为每种语言实现独立的 CST 到 common AST 转换器，每语言一个转换文件。
- 使用跨语言统一命名的节点表达声明、语句、表达式和类型结构。
- 尽量无损保留源码结构，节点与 CST 及源码区间双向关联。
- 语言特有语法通过受控扩展字段保留，不污染跨语言公共节点。
- 不负责作用域、名称解析、类型求值或语义规范化。

### 符号表

符号表负责语义名称空间：

- 在 common AST 之上建立项目、模块、包、命名空间、类型、函数和代码块作用域。
- 收集声明并生成稳定的符号标识。
- 将名称引用绑定到候选符号或唯一符号。
- 处理导入、可见性、遮蔽、重载、接收者和继承关系。
- 对无法唯一解析的引用保留候选集合与失败原因，不得强行绑定以制造误报。

### 统一 IR

统一 IR 负责在 common AST 与符号表之上构建面向分析的语义模型：

- 对 common AST 做语义规范化：desugar、显式化隐式控制流与隐式操作、规范化表达式。
- 将名称引用绑定到符号表符号，关联可求得的类型。
- 为每个 IR 节点分配稳定标识，并保留到 common AST 与源码区间的映射。
- 语言无法完全统一的语义通过受控扩展表达，不污染公共字段。
- 不直接完成 Call Graph 构建。

### Call Graph

Call Graph 负责调用关系：

- 节点表示可调用实体，边表示调用点到候选目标的关系。
- 每条边保留调用点、解析方式、置信状态和候选来源。
- 直接调用优先精确解析；动态调用保留候选集合。
- 未解析调用必须显式记录，不得静默丢失或绑定到无依据目标。
- 不承担通用数据流或污点传播职责。

- 未解析、部分解析和已解析状态必须明确区分，禁止使用零值混淆状态。

## 对外接口

对外能力按流水线各阶段暴露：

```go
ParseProject
BuildCommonAST
BuildSymbolTable
BuildIR
BuildCallGraph
BuildTypeHierarchy
BuildFunctionSSA
AnalyzePointers
AnalyzeTaint
VerifyPathFeasibility
MatchPatterns
DetectMissingChecks
EmitSarifReport
```

上述均为各模块的顶层入口函数，分别转发到对应模块设计文档定义的接口方法（如 `Parser`、`Converter`、`Builder`、`Lowerer`、`Analyzer`、`Engine`、`Verifier`、`Matcher`、`Detector`、`Emitter`）。具体 Go 接口、参数和返回结构由各模块设计文档确定。总体约束如下：

- 每一阶段都接收显式上下文并返回结果与诊断。
- 阶段结果应可独立测试，不依赖全局可变状态。
- 单文件失败不得无条件中止整个项目分析；必须返回可用的部分结果与诊断。
- 下游模块只依赖上游公开模型，不直接访问上游私有实现。
- 污点分析、符号执行路径可达性验证、语法模式匹配和缺失安全检查检测必须可通过配置独立开关，关闭某项时不影响其余阶段的结果与确定性。
- 上述入口中 SSA、指针分析、调用图为全量构建，作为检测器的事实底座；污点分析的“按需”仅指在这些全量结果之上只沿与查询相关的路径求解，不改变上游的全量构建性质，也不由污点分析反向驱动上游的部分构建。
- 相同输入、配置和依赖版本必须产生确定性结果。

## 处理流程

处理流程按前端基础阶段（模块 01–05）与分析与报告阶段（模块 06–13）依次推进，每个模块只消费上游已验证的公开结果。

### 前端基础阶段

#### 模块 01：Parser

1. 根据文件扩展名选择 grammar；`.h` 文件必须同时使用 C 与 C++ grammar 解析，不得依赖编译信息或项目配置。
2. 加载对应 Tree-sitter grammar。
3. 解析文件并收集语法错误、缺失节点和源码位置。
4. 输出统一包装的语法树结果。
5. 使用独立 fixture 验证五类语言的正例、负例、错误恢复和边界情况。

#### 模块 02：Common AST

1. 为每种语言实现独立的 CST 到 common AST 转换器，每语言一个转换文件。
2. 将各语言 CST 规范化为跨语言统一命名的抽象语法树节点，屏蔽 Tree-sitter grammar 细节差异。
3. 尽量无损保留声明、语句、表达式和源码结构，与源码一一对应。
4. 建立 common AST 节点与 CST 节点、源码区间的双向关联。
5. 语言特有语法通过受控扩展字段保留，不污染跨语言公共节点。

#### 模块 03：符号表

1. 从 common AST 建立作用域树。
2. 收集声明并分配稳定符号标识。
3. 解析导入、包、命名空间和跨文件可见性。
4. 绑定引用并记录唯一目标、候选集合或失败原因。
5. 对 C/C++ 重载、Java 继承与重载、Go 接收者与接口、Python 的 LEGB 作用域及 `global`、`nonlocal` 分别实现语言规则。

#### 模块 04：统一 IR

1. 以 common AST 与符号表为输入，为每种语言构建面向分析的统一 IR。
2. 对 common AST 做语义规范化：desugar、显式化隐式控制流与隐式操作、规范化表达式。
3. 将名称引用绑定到符号表符号，关联可求得的类型。
4. 为每个 IR 节点分配稳定标识，并保留到 common AST 与源码区间的映射。
5. 对等价语义使用跨语言一致的 IR 结构进行验证，无法统一的语义通过受控扩展表达。

#### 模块 05：Call Graph

1. 从 IR 中收集所有可调用实体与调用点。
2. 使用符号表解析直接函数和静态方法调用。
3. 对 C/C++ 函数指针和虚调用、Java 虚方法、Go 接口调用、Python 一等函数与动态属性调用建立候选边。
4. 对构造、初始化和隐式调用建立明确规则。
5. 输出已解析边、候选边和未解析调用统计。

### 分析与报告阶段

#### 模块 06：类型/类层次

1. 从符号表收集所有类型、接口、类和结构体声明。
2. 建立继承、实现、嵌入和成员归属关系，形成类型层次图。
3. 对 C++ 多继承与模板、Java 类与接口继承、Go 结构体嵌入与接口满足、Python 多继承与 MRO 分别实现规则。
4. 记录字段、方法和成员在层次中的定义与覆盖来源。
5. 无法唯一确定的父类型或实现关系保留候选集合，不得强行绑定。

#### 模块 07：函数内 SSA

1. 以 IR 中每个函数或方法体为单位构建控制流图。
2. 为局部变量插入 φ 函数并重命名，生成静态单赋值形式。
3. 保留每个 SSA 值到 IR 节点和源码位置的映射。
4. 明确区分局部变量、参数、字段访问和调用返回值等值来源。
5. 不做跨函数分析，跨函数信息由调用图和后续过程间分析承接。

#### 模块 08：局部指针分析

1. 在 SSA 之上识别对象创建、字段存储和字段加载点。
2. 为对象创建点分配抽象对象标识，建立指针指向关系。
3. 跟踪 `new`、`store`、`load` 之间的传播，解析字段级别名关系。
4. 保证被别名连接的值在数据流上连续可追踪，避免链路中断。
5. 无法确定指向的指针保留候选对象集合，并显式记录不确定来源。

#### 模块 09：按需污点分析

污点分析是当前建设的重点，率先在指针分析等基础之上落地。

1. 接收 source、sanitizer 和 sink 的规约，作为分析的查询输入。
2. 以 SSA、指针分析别名关系和调用图为基础，按需（on-demand）从 sink 或 source 出发触发求解，不预先展开全程序数据流。
3. 沿数据流和字段别名传播污点，遇到 sanitizer 时按规则清除或降级污点。
4. 对到达 sink 且未被 sanitizer 拦截的污点，输出带完整传播路径的 source→sink 数据流。
5. 传播依据不足或路径不确定时保留候选并显式标注，不得凭空补全以制造误报。

#### 模块 10：局部符号执行与主路径可达性验证

1. 接收污点分析给出的 source→sink 主路径作为待验证目标，只针对该主路径工作，不枚举无关路径。
2. 在自建的轻量 IR 虚拟机中解释执行统一 IR，全程不运行、不编译、不加载被分析项目的原生代码。
3. 沿主路径（可从 source 正向或从 sink 反向）收集分支条件、SSA 值约束和指针别名约束。
4. 用轻量约束求解只判定主路径约束是否可满足，不做无止境或与主路径无关的求解。
5. 约束可满足则确认路径可达；仅在可证明 UNSAT 时剪除；求解超时或存在未建模操作时保守保留为可能可达，不制造漏报。

#### 模块 11：语法模式匹配

1. 接收带元变量的语法模式规则，以 AST 与 IR 节点作为匹配对象。
2. 在语法树上匹配结构，元变量绑定具体子节点并在同一模式内保持一致性约束。
3. 支持对元变量施加名称、类型、常量或字面量等约束，缩小匹配范围以提高精确度。
4. 对命中位置输出带源码范围和元变量绑定的匹配结果，例如硬编码口令 `password = "..."`。
5. 匹配只基于语法结构与可用符号信息，不做跨函数数据流推断，避免无依据误报。

#### 模块 12：缺失安全检查检测

1. 按调用上下文或代码结构，将代码库中承担相同职责的相似片段聚为同类分组。
2. 借助语法模式匹配判定同组片段语义等价，只允许语法细微差别，不允许语义差别。
3. 统计同组片段中普遍存在的安全检查（如鉴权），建立该组的期望检查集合。
4. 找出缺失期望检查的个别片段并作为异常报告，例如六处中五处有鉴权、第六处缺失。
5. 分组样本过少或等价性无法确认时不报告，避免把正常差异当成异常制造误报。

#### 模块 13：SARIF 报告

1. 收集经路径可达性验证后的污点发现及其他分析模块产生的结果与诊断。
2. 将每个发现映射为 SARIF 的 `result`，规则信息映射为 `rule`，并按可达性判定标注结果置信度。
3. 将 source→sink 的完整传播路径映射为 SARIF 的 `codeFlows`，每一步保留文件、行列范围和消息。
4. 生成符合 SARIF 2.1.0 schema 的输出，保证工具、规则和位置信息可回溯到原始源码。
5. 相同分析结果必须产生确定性的 SARIF 输出，字段顺序和结果排序稳定。

## 错误处理

- Parser 必须保留 Tree-sitter 错误节点并尽可能输出部分语法树。
- Common AST 转换遇到不支持语法时必须生成带源码位置的诊断，不得 panic 或静默丢弃。
- IR 转换遇到无法规范化的语义时必须生成带源码位置的诊断，不得 panic 或静默丢弃。
- 符号解析失败必须区分“未找到”“存在多个候选”“上游语法错误”和“暂不支持”。
- Call Graph 无法确定唯一目标时必须保留候选集合；没有依据时保持未解析状态。
- 所有模块仅在内部不变量被破坏且无法恢复时返回致命错误。
- 批量项目分析必须汇总诊断，单文件错误不应默认终止其他文件处理。

## 性能与资源限制

- Parser 应支持单文件解析，并为后续增量解析保留扩展空间。
- 项目级索引不得要求一次性复制所有源码内容。
- AST、符号、IR 和调用图使用稳定标识关联，避免形成难以回收的对象引用环。
- 各阶段必须接受上下文取消信号，禁止不可中断的长时间分析。
- 各阶段必须内置计时与 profile 埋点并能输出结构化中间结果，以分别验证功能正确性和性能，埋点默认关闭且不影响正常分析。
- 性能基准与资源上限在对应模块获得真实 fixture 和基准数据后确定，不得提前虚构指标。

## 安全考虑

- 所有输入源码均视为不可信数据。
- 分析过程不得执行、编译或动态加载被分析项目中的代码；符号执行只在自建轻量虚拟机中解释统一 IR，不运行被分析项目的原生代码。
- 符号执行必须对路径长度、分支数量、虚拟机步数和约束求解时间设置可配置上限，超限时保守终止，不得无界求解。
- 必须防止畸形语法树、超深嵌套、超大文件和符号爆炸导致 panic 或无界资源消耗。
- 文件读取必须限制在调用方明确提供的项目范围内，不得跟随不受控路径读取任意文件。
- 诊断信息不得包含与当前分析无关的环境敏感信息。

## 测试设计

每个模块的测试数据必须位于模块自己的 `fixture/` 子目录，禁止把被测源码嵌入 Go 测试字符串。总体测试矩阵至少包括：

| 维度 | C | C++ | Java | Go | Python |
|---|---|---|---|---|---|
| 基础解析 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 语法错误恢复 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 声明与引用 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 跨文件解析 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 直接调用 | 必须 | 必须 | 必须 | 必须 | 必须 |
| 动态调用 | 函数指针 | 虚调用/函数指针 | 虚方法 | 接口调用 | 一等函数/动态属性 |
| 泛型能力 | 不适用 | 模板 | 泛型 | 泛型 | 类型参数/类型标注 |

每个阶段必须包含：

- 正例：验证应被识别的结构或关系，正报数量必须大于零。
- 负例：验证不会生成无依据结果。
- 边界：空文件、超深结构、错误语法、匿名结构和复杂嵌套。
- 变体：等价语义的不同语法形式。
- 回归：每个已修复问题对应独立 fixture。
- 确定性：相同输入重复运行结果一致。
- 误报统计：误报率必须低于 30%，且不得通过删除困难样例降低标准。

## 验收标准

整个流水线仅在以下条件全部满足后完成：

- **前端基础阶段**：C、C++、Java、Go 和 Python 均可通过 Tree-sitter 解析并输出源码位置准确的结果。
- **前端基础阶段**：五类语言均能转换为跨语言 common AST，公共节点无需下游读取 Tree-sitter 节点即可分析。
- **前端基础阶段**：符号表能够在 common AST 之上处理单文件和跨文件声明、作用域、引用与核心语言可见性规则。
- **前端基础阶段**：统一 IR 能在 common AST 与符号表之上完成语义规范化并绑定符号，供下游分析复用。
- **前端基础阶段**：Call Graph 能够识别五类语言的直接调用，并对动态调用输出有依据的候选集合。
- **分析与报告阶段**：类型/类层次能建立五类语言的继承、实现与成员关系，函数内 SSA 能为函数体建立静态单赋值形式。
- **分析与报告阶段**：局部指针分析能解析对象创建与字段存取的别名，按需污点分析能给出 source→sanitizer→sink 的完整数据流。
- **分析与报告阶段**：符号执行能在自建轻量 IR 虚拟机上对污点主路径做可达性判定，正确剪除可证明不可达的路径且不产生漏报。
- **分析与报告阶段**：语法模式匹配能用元变量约束命中硬编码口令等模式，缺失安全检查检测能在语义等价的相似片段中报出个别缺失的安全检查。
- **分析与报告阶段**：污点分析、符号执行、语法模式匹配和缺失安全检查检测均可通过配置独立开关。
- **分析与报告阶段**：报告模块能输出符合 SARIF 2.1.0 schema 且可回溯源码的确定性结果。
- 所有模块均有独立 fixture、有效正报、负例、边界测试和回归测试。
- 每个模块误报率低于 30%，所有适用的 Go 测试、静态检查和构建均通过。
- 设计文档、实现、测试与进度标记一致。
